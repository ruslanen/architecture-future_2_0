# Список проблемных мест
1. **Невозможность системы справиться с растующей нагрузкой**. 
Сейчас есть узкое горлышко DWH в виде устаревшего MS SQL Server 2008. Так как все сервисы работают именно с ним, а объем данных уже достиг сотни терабайт, то очевидно предположить, что база данных станет проблемным местом (если еще не стала). Плюс ко всему прибавляется новая нагрузка в виде новых компаний: банк, фармакология, электроника.
Дополнительно к этому еще минусы MS SQL Server 2008:
- нет шардирования и горизонтального масштабирования
- архитектура не рассчитана на объемы компании
- продукт больше не поддерживается (это означает, что нет фиксов безопасности)
- сильно ограниченный функционал (права доступа, интеграции).

2. **Возможные простои в работе бизнеса**.
Сюда можно отнести также устаревший DWH по тем же причинам, а также устаревшую шину данных в виде Apache Camel, т.к. он монолитный и нет долговременного хранения событий.
Иными словами, система может превратиться в тыкву в какой-то момент.

3. **Несоблюдение требований безопасности и ФЗ.**
Сюда можно отнести:
- репутационные риски: когда появятся новые компании и домены непонятно как будет осуществляться доступ к данным. Нельзя чтобы сотрудники видели информацию, которая не предназначена для них, данные могут утечь и компания потеряет репутацию;
- юридические риски: при утечке данных компания может столкнуться с судебными издержками.

3. **Сложности в работе сотрудников отдельных команд при работе с данными**.
Так как нет "единой точки правды":
- никто оне знает какие данные существуют вообще в компании
- каждый отдел хранит данные как хочет, делает свои копии данных
- тратится много времени чтобы разобраться в источниках
- могут быть ошибки в работе аналитиков
- снижается показатель time-to-market.

4. **Высокая стоимость оборудования и ПО, а также невозможность перехода в облако**.
MS SQL Server 2008 и Apache Camel масштабируются только вертикально.
Плюс лицензия MS SQL Server 2008 стоит дорого.

5. **Сложности интеграции новых доменов**.
Сейчас при добавлении новых компаний требуется вшивать логику в монолитный DWH. 
Это усложняет работу и увеличивает технический долг.

|---|---|---|

# Основные идеи изменений (дополнение к C4)
1. Переходим на Data Mesh подход с разделением ответственности между доменами.
Основной сервис для имплементации - DataHub.
Предполагается, что каждая команда домена будет сама отвечать за свои данные (медицина, финтех, HR и т.д.).
Для понимания того, где хранятся данные по доменам будем использовать тот же DataHub. Предполагается, что любой сотрудник сможет получить доступ к метаданным (при наличии прав).
Тегирование данных также осуществляется через DataHub со следующими типами:
- персональные данные
- медицинские данные
- финансовые данные.
Тегирование необходимо, чтобы обеспечить корректные политики RBAC/ABAC и выполнять требования ФЗ к данным.
2. Контроль доступа к данным реализуется за счет:
- настройки пользователей и ролей в DataHub
- настройки RLS прав в PowerBI
3. Хранилище реализуем по типу Data Lakehouse с премуществами DWH и Data Lake учитывая специфику работы с данными в огранизации т.к. требуется поддержка работы и ML/AI-сервисов и аналитических запросов. Релизация Data Lakehouse достигается за счет:
- разделения слоев на S3 (дублируем данные с разном виде обработки: сырые, очищенные от дублей и мусора, трансформированные под витрины). Для этого используем ETL в Kafka Connect.
4. До конца непонятно как данные попадают в MS SQL Server 2008 поэтому он оставлен как устаревшая технология, которая впоследствии будет упразднена. Предполагается полный отказ от СУБД в пользу объектного хранения или СУБД другого типа (будем осушать источник), т.к. сейчас это является узким горлышком в инфраструктуре организации в виде монолитного DWH, которое не масштабируется.
5. Предполагается, что все внутренние сервисы в организации, которые генерируют данные, будут писать сообщения в Kafka. Из Kafka забирать сообщения будет Kafka Connect и складывать в объектное хранилище. Здесь мы отказались от Apache Camel т.к. это также  устаревшая технология и имеет минусы в виде:
- отсутствия возможности масштабирования
- отсутствия CDC-стандарта
- сложность мониторинга.

# Дополнение

5. Мы отказались не от Apache Camel как технологии, а от текущей реализации ESB, построенной на старой версии Camel.
Этот монолит:
- плохо масштабируется
- не поддерживает событийную интеграцию и CDC
- затрудняет мониторинг

При переходе на новую архитектуру мы используем Kafka как транспорт.
Вся логика из ESB будет распределена:
- интеграции - через Kafka Connect
- трансформации - можно вынести в потоковые фреймворки если у нас есть много бизнес-логики в реальном времени (Kafka Streams)
- бизнес-процессы - в соответствующие микросервисы или BPM-систему

Таким образом, мы уходим от централизованного монолита (ESB) к распределённой архитектуре, где ответственность делится между доменами.
